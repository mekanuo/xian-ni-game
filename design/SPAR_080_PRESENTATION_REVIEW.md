## P2：余弹／结清后的暂停仍推进镜头

位置：`src/game/scene.ts:213–235`，`updateSparCamera`。

定位／active 分支的 `setZoom` 和 `centerOn` 均检查 `!paused && !dialogue`；相邻 settling／无 run 分支却无相同检查。`WorldScene.update` 在暂停时继续执行显示更新，因此模型被冻结不等于此镜头被冻结。

复现条件：实际射出后收手，趁跟随中心还未收敛点暂停。余弹位置与玩家不动，else 分支每帧仍以 .12 向玩家跟随目标缓动。若在结清、探索缩放尚未收敛时暂停，`!run` 的缩放也继续变化。例如原中心与目标相差100世界单位，默认首个暂停显示帧仍前进12单位；不是需要玩家再拖图才会发生。

这违反美术方向“暂停／恢复接同一阶段和尺度”的约束，但不会推进余弹碰撞或改变本轮结果。低动效下 blend=1 还会立即完成跳转，不能视为自然冻结。

最小修正边界：冻结练场自动镜头在暂停／对白时的缓动；保留主动看路、C／回到身边、必要 resize 重排。不要将旧地图的所有镜头行为一并改写。

修后应检查 settling 暂停前后 zoom 与 view 不变、实际恢复才续行；结清回探索的暂停亦如此，并保留主动拖图能够观察。

## P2：静止护符前侧人物仍用行走朝向镜像

位置：`src/game/scene.ts:330–339`；`src/game/presentation.ts:4–9`；真实状态来源 `model.ts:534–537,716–717`。

scene 为静止护符计算 `bodyAngle=wardFacing`，但 `setFlipX(back ? cos(bodyAngle)<0 : pose.flipX)` 只在背侧使用这一朝向。前侧 `pose.flipX` 来自玩家最后的 `facing`。护符展开后真实移动更新 facing，并不更新 wardFacing，所以两者合法地可以相反。

可达序列：向东撑符 → 向西走小段 → 停下且六秒护符尚存。此时 wardFacing=0、facing≈π、motionMoving=false，back=false，人物前侧 flipX=true 朝西，实际护符弧面仍朝东。反向亦成立；刚施术立即截图时 facing 尚等于 wardFacing，不容易暴露此问题。

这是身体／手势与实际防护方向的局部显示不一致，不是格挡判定错误，不能通过转动模型 wardFacing 或缩窄护符几何来修。

最小修正边界：练场静止护符的前侧镜像也采用实际 wardFacing；移动时继续以真实行进方向表现。旧地图无背侧帧且原来采用 pose.flipX，本次不能顺手改变其角色动作合同。

修后实际输入至少需包含两种相反的“撑符—反向移步—停下”，同时采护符弧面和身体；只断言 frame 名或模型 wardFacing 不足以证明手向相符。

## cameraManual 生命周期：现状及验收限制

`scene.ts:139` 拖动设 cameraManual=true；`:216` 优先返回，不自动夺回镜头。`:243` 回身、`:301` 键盘移动会清手动状态；普通地面点击、选择来向只清 panMode／dragStart，不清 cameraManual。

因此主动拖离后再点地行走，不自动回跟随；触屏须用“回到身边”，键盘 WASD 则直接恢复。这个差异是现有控制行为，结合设计明确保留的“手动拖离后用回身”，本审查不把它判成新回合软锁。手机验收必须包括真实回身按钮，不能一直用 WASD 代替这一控制。

约定前仍保持手动镜头时，进入 positioning 也不会强制切到600范围；若期望每次约定都强拉回来，会与当前主动观察的优先级不同。本审查不擅自改合同。自动模式下活动构图根据实际 HUD 底边和 action-dock 顶边计算，代码具备此条件仍不证明矮窗／手机实际手脚均无遮挡。
